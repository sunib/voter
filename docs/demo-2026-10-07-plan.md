## 3. Voting for some, then for all

**RBAC is the decision; the page only explains it.**

- `participant-rbac.yaml`: `quizsubmissions` loses `create` in the
  `voter-audience` Role (it keeps `get`). A new Role, `voter-audience-ballot`,
  holds `create` on `quizsubmissions`. Like `voter-audience-coffee-admin`, the
  Role lives in Git and its bindings do **not**: the operator's browser makes
  them.
- `/room` gets a second panel, **Who may vote**, with one switch per group:
  "Everyone" (the Room's `audienceGroup`) plus one per answer of the Room's
  question, read live from `spec.question.answers`. Each switch creates or
  deletes RoleBinding `voter-audience-ballot-<group suffix>` (for example
  `…-frontend-vue`). For a bit of fun, each switch shows how many participants
  picked that answer (a count over `Participant.spec.groups`).
- The vote page asks the API server before anyone types an answer
  (`useAuthorization`: may I `create quizsubmissions`?). On a no it shows a
  dedicated card, not a submit error:
  > **This round isn't open to you (yet).** Only some groups may vote right
  > now. You're in: *Svelte*. The presenter can open it to everyone.

  It doesn't poll. A participant can't watch RBAC: they may not read
  RoleBindings, and a SelfSubjectRulesReview is asked, not watched. So after
  every switch change `/room` writes the groups that may vote onto each round
  as annotation `voter.configbutler.ai/ballot-groups`, and every phone already
  streams the rounds. The page asks the API server again only when that marker
  moves. RBAC's answer is still what the page renders.

  When the operator flips a switch, the card turns into the ballot in front of
  the room, and back again when the switch is closed. That's the punchline. The
  flip lands in Git as one `demo1` commit: the RoleBinding next to the rounds'
  new marker.
- A 403 from RBAC at submit (a switch flipped back mid-answer) gets the same
  card. Admission refusals keep their own messages.
- `canVote()` (connector check) stays: it keeps the operator's "you are not a
  participant" message separate from "your group may not vote".
- Plumbing: `AUDIENCE_BALLOT_ROLE` in `voter/config.go` and `/config.json`,
  beside `AUDIENCE_COFFEE_ADMIN_ROLE`, plus the env var in `app.yaml`.

Rights are checked per request. A RoleBinding change takes effect on the next
click, with no re-login. Group membership is fixed in the token, which is why
the switch moves bindings rather than people.

## 4. Coffee: one person first

- `/room`, in the existing "What the audience may do" panel: **Pick someone**.
  It lists the Room's Participants (not revoked), picks one at random and
  shows the name large enough to read out. **Grant** creates RoleBinding
  `voter-audience-coffee-admin-person` to Role `voter-audience-coffee-admin` for
  that **User**. **Pick again** replaces it, and **Revoke** deletes it. The
  room-wide switch is unchanged and independent.
- The user name: the apiserver names a participant `demo:` + Dex's `sub`. For
  the authproxy connector Dex's `sub` is deterministic: base64url (no padding)
  of the protobuf `{1: user id, 2: "room-pass"}`. The user id is the
  Participant's name without its prefix (Room Pass sends it as
  `X-Remote-User-Id`). **Verify against one real participant** (`/me` shows
  `subject`) before relying on it. A wrong guess grants nobody anything, and
  the editor's refusal would show it on stage.
- Rejected: putting the person in a `demo:barista` group by editing
  `Participant.spec.groups`. It only takes effect at their next sign-in, so it
  can't be done live.
- The commit that follows carries that person's name. That's the reveal, as
  before.
